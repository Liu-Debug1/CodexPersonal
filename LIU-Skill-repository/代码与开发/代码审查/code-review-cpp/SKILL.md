# 代码规范审查规则

> 规范来源：`D:\桌面\研0记录\代码规范相关说明.docx`（原件备份：`references/代码规范相关说明.docx`）

---

## 1. 变量命名（三段式大驼峰）

**格式**：`作用域_模块_含义_类型`

**作用域前缀**：
- `g` — 全局变量（本工程所有 .c 可用）
- `l` — 局部变量（仅函数内部使用）
- `m` — 成员变量（类中使用）

**模块简写**（已知）：
| 模块 | 简写 |
|------|------|
| 定位 | LC |
| 规划 | PLN |

**含义**：首字母大写大驼峰，建议适当缩写，如 VehPosF（VehiclePositionFiltered）、SteerAngCmdFf

**类型后缀**：
| 后缀 | 类型 |
|------|------|
| `b` | bool |
| `u8` / `u16` / `u32` | 无符号 8/16/32 位 |
| `s8` / `s16` / `s32` | 有符号 8/16/32 位 |
| `db` | double |
| `f` | float |
| `p+类型` | 指针，如 `ps8` 表示 s8 类型指针 |

**正例**：`gLC_VehPosF_db`

**审查要点**：
- 三段是否完整（作用域_模块_含义_类型）
- 作用域前缀是否正确
- 类型后缀是否正确（bool → b, int → 对应位宽, double → db, 指针 → p+类型）
- 含义部分是否用大驼峰

## 2. 函数命名（两段式小驼峰）

**格式**：`模块_含义` 或 `含义`

**规则**：
- 小驼峰（首字母小写，后续单词首字母大写）
- 单词间不连下划线
- 动词开头

**常用动词前缀**：
- `get...()` — 获取值
- `find...()` — 查找元素
- `calc...()` — 计算
- `set...()` — 设置属性
- `update...()` — 更新状态
- `is...()` — 判断是否成立
- `init...()` — 初始化

**正例**：`getUserById()`, `processPayment()`, `setBackgroundColor()`, `isFileExist()`

**审查要点**：
- 是否两段式小驼峰
- 是否动词开头
- 是否误用下划线连接单词

---

## 3. 类命名和定义

**类声明**：单段式大驼峰
- 正例：`UserProfile`, `PaymentService`

**类实例定义**：两段式大驼峰 `类名_C`
- 正例：`RollerPlanner_C`, `SensorFusion_C`

**类中函数**：参照函数命名规范，初始化放 `init` 开头函数中

**审查要点**：
- 类名是否大驼峰、单段式
- 实例后缀是否 `_C`
- 类中函数是否遵循函数命名规范

---

## 4. 工程结构要求

- 每个工程只允许一个 main 函数
- 工程间变量交互**只能用消息**，不得直接调用
- 需要控制多个功能块时序 → 必须放同一个工程下
- main.c 只包含初始化 + 时序控制，不放业务代码

---

## 5. 注释规范

| 场景 | 注释方式 | 说明 |
|------|---------|------|
| 变量 | `//` 单行注释 | |
| 函数 | `/* */` 多行注释 | 放在函数声明开头 |
| 函数内代码结构 | `// #1.1` 格式 | 标注代码层级 |
| BUG 修改 | 标注 BUG 编号 | 代码和 Git commit 都要标 |

**函数注释模板**：
```cpp
/*
功能: 比例阀的PID控制
定义: WLT, 2020.06.11
修改: WLT, 2020.06.11
*/
```

**审查要点**：
- 变量注释是否用 `//`
- 函数是否用 `/* */` 多行注释
- 函数注释是否包含"功能、定义、修改"三要素（缺了提醒）

---

## 6. 宏定义规范

**适用场景**：
- 模式切换（仿真/实车）
- 大量重复调用的同一参数

**命名**：全大写 + 下划线分割，如 `MAX_BUFFER_SIZE`

**存放位置**：只在一个 .h 文件中定义，其他文件 include 即可

**模式切换示例**：
```cpp
#define PLT_VEHICLE   0  // 实车测试
#define PLT_SIMULATION 1 // 仿真
#define PLT_MODE      PLT_VEHICLE
```

**审查要点**：
- 宏名是否全大写+下划线
- 是否在 .h 中定义
- 模式切换宏是否预先定义了所有选项

---

## 7. 代码结构

**核心原则**：顺序结构为主
- 初始化 → 主循环 → 后处理
- 主循环内部也保持顺序结构
- 需要分支时：同一入口进，汇总同一出口出，然后继续顺序执行

**审查要点**：
- 是否有 goto / 多处 return 等破坏顺序结构
- 分支结构是否从同一出口汇合

---

## 8. 其他规则

- 数据记录统一在 `data_log` 文件中
- 头文件统一放在一个头文件工程里，提高可移植性
- 全局时间统一：主函数外单独写算时间函数，所有代码都调这个
- include 整理：基础库统一放在一个公共 .h，其他 .c 只需 include 这个公共 .h + 少数独特 .h
- 消息类型单独放消息 cpp 里
- 纯公式计算单独放计算 cpp 里
