# Prompt Optimizer

将原始需求变为范围明确、可验证、能减少返工的 Codex 提示词。保留用户真实意图和已有约束，不虚构项目事实、文件、依赖、指标或权限。

## Workflow

1. 判断请求模式。
   - 用户要求优化、改写、编写提示词时，进入优化模式。
   - 用户明确说“优化后直接执行”时，先在内部形成优化后的任务规格，再执行任务。执行期间仍遵守项目 `AGENTS.md`、确认要求和安全边界。
   - 用户已明确要求直接完成任务，且没有要求提示词帮助时，直接处理任务，不插入优化环节。
   - 用户说“优化代码”“优化性能”时，将其视为工程优化任务，而不是提示词优化。

2. 提取以下信息，并优先复用当前对话、工作区和项目规则中已知的事实。
   - 目标：最终要解决的问题或交付物。
   - 范围：目标文件、模块、数据、系统或研究对象。
   - 约束：禁止项、兼容性、安全、格式、时间或成本限制。
   - 完成标准：验收条件、测试、证据或输出质量要求。
   - 交付：用户要直接执行、方案、代码、报告、命令、表格还是解释。

3. 只补充真正影响结果的缺口。
   - 缺少关键范围、验收标准或安全边界时，提出不超过 3 个简短问题。
   - 若可以安全地按常见工程做法继续，则明确列出“假设”，不要为非关键细节阻塞任务。
   - 不把无关背景、泛化的角色设定或冗长步骤塞入提示词。

4. 编写可直接执行的提示词。按任务风险按需使用以下字段，删除不相关的字段：

```text
目标：
上下文：
范围：
约束：
完成标准：
验证：
交付形式：
```

## Task-Specific Guidance

### Code And Engineering

- 要求先读取目标项目的 `AGENTS.md`、相关实现和测试约定。
- 指出输入边界、错误处理、并发、资源、实时性或安全风险中真正相关的部分。
- 明确修改范围和不修改范围，并给出相称的验证命令或测试标准。

### Research And Technical Analysis

- 区分已验证事实、待验证假设和建议。
- 指定证据来源、比较对象、评价指标和复现条件。
- 对 ROS、控制、嵌入式或车辆相关任务，按需加入安全、实时性、接口边界和真机验证要求。

### Documents And Writing

- 指定读者、用途、语言、篇幅、保留结构和必须覆盖的信息。
- 对现有文档，明确哪些内容、标题层级、格式或引用不能改变。

## Output

默认使用与用户相同的语言，按以下顺序输出：

1. 一句话说明补齐的关键内容。
2. `优化后提示词`：用单个代码块给出可复制版本。
3. `假设或待补充项`：仅列出会影响结果的项目；没有则省略。
4. 当完整版本较长且用户可能反复使用时，附 `简短版`。

不要承诺执行优化后提示词未授权的外部操作。涉及凭据、外部服务配置、发布、删除或其他不可逆操作时，仍在实际操作前征求确认。

## Example

原始请求：

```text
帮我看看导航不稳定。
```

优化方向：补齐系统范围、证据来源、输出形式和不执行边界；不虚构具体机器人型号、参数文件或故障原因。

```text
目标：分析当前 ROS 导航不稳定的可能原因，并给出按优先级排列的排查步骤。

范围：检查定位、TF、传感器输入、里程计、代价地图、局部规划器和速度控制链路中与现象直接相关的部分。

要求：
- 先读取相关 launch、参数文件和节点日志或源码；不要仅按参数名猜测。
- 区分已验证事实、待验证假设和建议。
- 每个候选原因说明需要检查的文件、参数、话题或日志证据。
- 指出必须通过真机、录包或日志验证的结论。

交付：先给最可能的 3 个原因和最小排查步骤，再给一条从传感器输入到速度指令的简洁数据流。

不要做：不修改配置、不启动节点、不执行真机操作。
```
