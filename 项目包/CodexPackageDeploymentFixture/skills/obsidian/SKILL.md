# Obsidian

把 Obsidian 看成两层：

1. Vault 层：查找、创建、移动、删除、重命名笔记。
2. 内容层：整理笔记结构、统一风格、增强可读性。

这两个层面现在统一由本 skill 处理，不再拆成多个个人风格 skill。

## 任务分流

先判断用户要的是什么：

- 只是找笔记、建笔记、移动笔记、批量改名：走 Vault 操作流。
- 只是整理现有笔记内容：走内容整理流。
- 既要移动笔记又要改内容：先处理 Vault，再整理内容。

## Vault 操作流

Obsidian vault 本质上就是普通文件夹，但优先用 `obsidian-cli` 做会影响链接的操作。

### 优先级

1. 搜索和定位：优先 `obsidian-cli search` / `obsidian-cli search-content`
2. 创建、移动、重命名、删除：优先 `obsidian-cli`
3. 纯内容编辑：直接改 `.md` 文件即可

### 原则

- 不要猜 vault 路径，优先用 `obsidian-cli print-default --path-only` 或现有上下文确认。
- 不主动改 `.obsidian/` 配置目录，除非用户明确要求。
- 移动或重命名笔记时，优先用 `obsidian-cli move`，因为它会更新常见链接。
- 涉及批量整理时，先确认影响范围，再统一执行，不要边搜边乱改。

### 常用操作

- 搜索笔记名：`obsidian-cli search "query"`
- 搜索正文：`obsidian-cli search-content "query"`
- 新建笔记：`obsidian-cli create "Folder/Note" --content "..."`
- 移动笔记：`obsidian-cli move "old/path" "new/path"`
- 删除笔记：`obsidian-cli delete "path/note"`

## 内容整理流

整理 Obsidian 笔记时，目标不是“排版花”，而是让笔记更适合长期复习和工程复用。

### 核心目标

- 可读：第一屏就能看出这篇笔记在讲什么。
- 可复用：半年后再看，仍然能快速恢复上下文。
- 可检索：标题、列表、表格、代码块能形成清晰锚点。

### 总体风格

- 结论先行，解释跟上。
- 工程导向，少聊感受，多写判断依据、边界和坑点。
- 克制排版，不把笔记写成海报。
- 同一篇笔记的风格保持一致，不要一半是手册一半是聊天记录。

## 结构规则

当内容足够完整时，优先组织成这个顺序：

1. 结论
2. 解释
3. 示例
4. 坑点或边界
5. 复盘或关联场景

不是每篇笔记都必须五段齐全，但至少要让读者看得出：

- 这是什么
- 为什么这样
- 怎么用
- 哪些地方容易错

### 标题粒度

- `##` 应该对应一个完整知识单元。
- 不要为了“看起来规整”把一句话拆成多个标题。
- 同级标题粒度要一致，不要把“概念总览”和“某个寄存器单 bit 含义”放在同一级。

## 段落转列表

只转换密集 prose，不动这些内容：

- 代码块
- 表格
- callout
- ASCII 框图
- Mermaid
- wikilink
- embed

### 什么时候该转列表

- 一段话里并列罗列了多个要点
- 明显是步骤
- 明显是因果链
- 明显是对比项

### 转换规则

- 并列项：转无序列表
- 步骤项：转有序列表
- 因果链：用缩进列表表达层级
- 多维对比：优先用表格

### 不要过度列表化

这些通常保留段落：
- 单句总结
- 过渡句
- 连续推理、拆开会破坏逻辑的解释

## 代码图片转代码块

整理 Obsidian 笔记时，如果图片主体是代码，直接把它转成对应技术栈的 fenced code block。

### 转换规则

- 语言标记优先按内容选择 `c`、`cpp`、`python`、`text`
- 只有高置信判断为代码图片时才转换
- 转成代码块后删除原图片引用

### 保留边界

- 流程图、架构图、示意图、对比图等非代码图片保留原样
- 无法高置信判断是否为代码时，保留原图，不强删
- 不凭空补写图片中没有体现、上下文也没有明确给出的业务逻辑

## 标题编号规则

整理标题时，统一成中文编号体系：

- `#`：文档标题，不编号
- `##`：一、二、三
- `###`：1.1、1.2、1.3
- `####`：1.1.1、1.1.2
- `#####`：1.1.1.1

### 编号原则

- 同一层级连续编号，不跳号。
- 子标题编号必须跟随父级编号。
- 只改标题行，不顺手修改正文内容。


## 元素选型规则

整理笔记时，用什么元素，取决于信息类型，而不是个人喜好。

- 结论、边界：可用粗体强调
- 标识符、命令、路径：用行内代码
- 可执行示例：用带语言标识的代码块
- 多维对比：用表格
- 风险、提醒、补充：用 callout
- 结构关系、数据流：优先 ASCII 框图，必要时再用 Mermaid

## 推荐处理顺序

如果用户要“全面整理一篇 Obsidian 笔记”，按这个顺序做：

1. 先看整篇结构，判断标题层级是否合理
2. 把密集段落改成更清晰的列表或表格
3. 统一标题编号
4. 补关键强调、代码块语言、必要 callout

这样做的原因是：结构先稳住，局部美化才不会反复返工。

## 与其他 Obsidian skill 的分工

- `obsidian-markdown`：负责语法细节，如何把 wikilink、embed、callout、frontmatter 写对
- `json-canvas`：处理 `.canvas`
- `obsidian-bases`：处理 bases、视图、公式

本 skill 负责的是：

- Obsidian vault 操作路径
- 整篇笔记如何组织
- 段落何时转列表
- 代码图片何时转成代码块，以及语言标识怎么选
- 标题如何统一编号

## 反模式

看到这些情况要主动收敛：

- 标题碎片化，一页里全是 `###`
- 一整屏全是纯文字，没有任何锚点
- 为了“生动”给每一条都加 emoji
- 本来适合表格的内容硬写成长段落
- 改笔记时顺手破坏代码块、表格、callout 结构

## 完成前自检

- 第一屏能否看出主题和结论
- 标题层级是否统一
- 长段落是否已经压缩成更好扫读的结构
- 代码块是否保留且语言标识完整
- 是否保住了 wikilink、callout、表格和代码块
